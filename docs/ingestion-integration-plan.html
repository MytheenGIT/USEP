4Missing interfaces and contracts

None of these exist on either branch today. They are what the two layers must agree on before the refactor, ideally in one short ADR.

Connector contract foundation to define, connectors to implement
# ports/connector.py (proposed)
class Connector(Protocol):
    source: str
    async def scopes(self, ctx: RunContext) -> list[Scope]: ...
    def fetch(self, ctx: RunContext, scope: Scope, since: str | None, lane: Lane) -> AsyncIterator[FetchedBatch]: ...
    async def enumerate(self, ctx: RunContext, scope: Scope) -> dict[str, str]:   # object_id -> version, for reconciliation
        ...
    cursor_codec: CursorCodec                                                       # opaque cursor <-> source query value

@dataclass
class FetchedBatch:
    raw_objects: list[RawObject]      # object_type, object_id, payload: what the raw writer stores
    documents: list[SourceDocument]   # normalised view for later stages
    next_checkpoint: str | None
Cursor store must carry scope and lane foundation

His domain defines a cursor per (tenant, source, scope, lane), but CursorStorePort only takes source. With several Jira projects or GitLab repositories, one cursor per source would let a fast project hide a slow one's changes. Change the port to get_cursor(source, scope_id, lane) and set_cursor(source, scope_id, lane, cursor).

Writer outcome and a typed envelope foundation
  • RawPayloadWriter.write() returns only a string (quarantined:// or failed:// sentinels). CursorManager.advance needs real outcomes. Expose write_result() -> WriteResult and keep write() as a thin wrapper.
  • Replace the magic raw_payload["_usep"] dict with a typed RawEnvelope argument. His own docstring says the dict form is "pending connector-owner confirmation" and refers to docs/plans/ASSUMPTIONS.md, which is not committed on any branch. Confirm this decision in writing.
HTTP transport port and run context foundation defines, adapter implements
  • HttpTransportPort.send(request) -> SendOutcome, implemented in adapters/httpx. His runtime deliberately imports no httpx, so the adapter is where httpx lives. This keeps connectors vendor-free and testable with a fake transport.
  • RunContext: tenant id, run id and trace id, lane, clock, observer, rate limiter and secret resolver, passed to every connector call.
Credential, registry, orchestrator shared
  • Credentials: per-source settings models with *_ref fields (his Settings says per-source keys were deferred to "the connector work", which is this work).
  • Registry: ConnectorRegistry.register(source, factory), so adding a connector does not touch the orchestrator.
  • Orchestrator: a SyncRunner that owns scope selection, lane, cursor start and advance, the state machine (his transition() exists but nothing calls it) and reconciliation. No branch owns this today.
  • Dev adapters: local-filesystem object store, in-memory raw index, local key store, log event bus. Only the Vault adapter is real, so nothing can be run end to end yet.

5Recommended architecture

Connector layer

Owner: connector developer
  • Source endpoints and auth header shape
  • Pagination choice (which helper)
  • Cursor codec, scope discovery, enumerate
  • Mapping to raw objects and SourceDocument
  • No retries, no sleeping, no storage, no secrets

Runtime layer

Owner: foundation
  • Rate limit per tenant, source, account, lane
  • Retry, back-off, Retry-After, defer and dead letter
  • Response classification
  • Pagination helpers, observer events
  • Imports no vendor SDK

Storage layer

Owner: foundation
  • Raw writer: scan, hash, encrypt, dedupe, publish reference
  • Ports: object store, raw index, key store, event bus, quarantine, cursor store
  • Adapters: S3, Postgres, Kafka, KMS, plus dev ones

Orchestration

Owner: shared, decide in phase 0
  • Scheduling and manual trigger
  • Lane, window, backfill
  • Cursor start and advance rule
  • Connector state machine, reconciliation
  • Audit and run result

Dependency rule: connectors depend on domain, ports and runtime only, never on storage adapters or on each other. The orchestrator depends on everything through ports. Configuration and secrets are cross-cutting: they are resolved at the composition root and by the runtime transport, never inside connector logic.

9Corrections to the starting assumptions, and what I did not verify

Not accurate on my side

  • "Remove connector retry logic": there is none. The foundation adds retries rather than replacing mine.
  • "Return a standard SourceDocument": already true; every connector returns a SourceDocument subclass. What is missing is hosting the base class in the foundation.
  • "Implement a common BaseConnector": a SourceConnector Protocol exists. It needs extending (scopes, batches, enumerate), not creating.

Underestimated on the foundation side

  • It needs more than a registry, a contract and hooks: cursor scope and lane, writer outcomes, an orchestrator, dev adapters and the HTTP transport adapter.
  • It is not yet runnable end to end.
What I did not verify
  • I did not run the foundation's test suite (99 test functions) or my own against it, and did not wire the two together.
  • The Jira JQL date-format claim is from my knowledge of JQL, not tested against a Jira instance. I confirmed only that the foundation's overlap function returns ISO timestamps with a T and an offset.
  • docs/plans/ASSUMPTIONS.md and the "Phase 1 plan" sections his code cites are not in the repository, so some of his design decisions are known only from code comments.
  • Effort numbers are estimates, not measurements.
