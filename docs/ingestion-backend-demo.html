USEP ingestion layer: backend demo guide

Universal Semantic Engineering Platform · from the source API to the encrypted raw store · backend only · 27 Nov 2026

The ingestion layer reads Jira, Confluence, GitLab, GitHub, ServiceNow and Figma (read-only), and lands every record as an encrypted, deduplicated, audited raw object with a resume cursor. Nothing downstream (normalising, chunking, the graph) is part of it. This page says what was built, how to show it, which HLD/LLD questions it answers, and where the documents disagree.

3Security and safety rules applied

  • Raw objects encrypted per object (envelope encryption)
  • Source tokens never stored, logged or returned
  • Typed server URLs must be https; private addresses blocked
  • Scope entries strictly validated (no query injection)
  • SSH keys: temp file mode 0600, host keys must be supplied, refused otherwise
  • Figma blocked until the DPIA flag is set (ADR-025)
  • Secrets and personal data are quarantined, not stored
  • Hash-chained, append-only audit
  • Tenant id on every configuration, checked on read
  • Fails closed: no admin credentials means no sign-in
  • Run snapshots drop any setting named token, secret, password or email
  • Typed errors with a trace id, no stack traces

4Demo script (about 8 minutes)

  1. Show the config. Only the sources you switch on run. Switch Jira on; show that a half-filled Jira stops start-up with a clear message.
  2. Run a sync. Use the sync endpoint or tools/fetch_jira.py against sematic-test.atlassian.net, project KAN. Show the run record and the audit event.
  3. Show the files. Open services/connectors/output/raw. The files are unreadable ciphertext on purpose.
  4. Prove what is inside. Run tools/read_raw.py on one object: decrypts to the original Jira JSON.
  5. Run it again. Nothing new is written: unchanged content is skipped by content hash, and the cursor moved forward.
  6. Show a secret being caught. A record containing a card-like number lands in quarantine, not in the store.
  7. Show switchability. Same run with RAW_STORE=s3 against a mock bucket (tests) gives the same keys and bytes.
Be upfront. Real Jira is the only live source. S3 was tested against a mock (moto), SSH only against a local repository, GitHub and ServiceNow against recorded API shapes.

5Likely HLD and LLD questions, answered

Where does raw data land and is it safe?
As encrypted objects in the raw store: files in the repo for now, S3 by changing one setting. Each object has its own data key, wrapped by the tenant key. The key is saved to the raw index before the object is written, so an object can never exist without its key.
What if the same record is read twice?
Same content hash means no new object and no new event. A changed record becomes a new object (the hash is in the object key), so history is kept.
What if the service crashes halfway?
The cursor is moved only after the publish is acknowledged, so a restart re-reads from the last checkpoint. Duplicates are absorbed by the content-hash dedupe.
What if a source is slow or fails?
Rate limit per source, retry with backoff, Retry-After honoured. After 5 attempts the call is logged and audited and the cursor stays put. One source failing does not stop the others.
Do two processes or two scopes interfere?
No. Cursors are per source, scope and lane, and use atomic upserts. A 12-process run on real Postgres found and fixed a merge race.
How are late edits handled?
The cursor has an overlap window, so records updated near the checkpoint are read again. Dedupe makes that cheap.
How do you keep secrets and personal data out?
The writer scans before storing. A hit is quarantined with a record, not stored. Source tokens are never stored or logged.
Is there an audit trail?
Yes: one hash-chained event per run, stored in an append-only table, and a snapshot of the run settings with secrets removed. Retention and the periodic hash export are open (D-09).
Can an admin choose which sources and scopes?
Yes. Every source is optional. Jira takes project keys and JQL, Confluence space keys, GitLab and GitHub repositories (listed, linked, or all reachable), ServiceNow tables.
What is the event that goes downstream?
A raw-object-published event: source, scope, object id, version, content hash, object key, retrieval time and the source permissions (source_acl). Kafka is behind a port; the adapter is not built, so it is logged.
How is access control carried?
Source permissions are collected and carried on the event. Mapping them to acl_ref is open (D-06); until then everything is owners-only, the LLD's rule for unmapped permissions.
Is it ready for production?
No. It needs the Kafka adapter, Vault and key management, the S3 bucket with Object Lock, migrations, and the open decisions below.
